# هيكلة AKTOOL: النواة، الذكاء الاصطناعي، السيرفر، البوت

تاريخ: 2026-10-11. مبنية على وثيقة AKTOOL مع قرارك: محلي وأونلاين بالتزامن، والنسخة الأونلاين الأولى لك وحدك.

## 1. الصورة الكاملة

```
                ┌──────────────── عملاء (Clients) ────────────────┐
                │  واجهة محلية (Streamlit ثم romHEX14)            │
                │  بوت Telegram  (لاحقاً: Mini App)               │
                │  أي أداة خارجية عبر REST API                    │
                └───────────────┬─────────────────────────────────┘
                                │  HTTP  /api/v1  (نفس العقد للجميع)
                ┌───────────────▼─────────────────────────────────┐
                │              AKTOOL Core (FastAPI)              │
                │  Vault │ Identity │ Importers │ Validators      │
                │  Knowledge DB │ Review │ JSON Factory │ Sync    │
                │  AI Adapter ──► Ollama (أو أي مزود آخر)         │
                └─────────────────────────────────────────────────┘
        نفس الكود يعمل في وضعين:
        • local  : على جهازك، 127.0.0.1، SQLite، بدون إنترنت
        • server : على VPS، HTTPS + مفتاح API، يخدم البوت
```

**المبدأ الأهم:** النواة واحدة، وكل الواجهات عملاء لها. البوت لا يحتوي منطقاً خاصاً، بل يستدعي نفس الـ API الذي تستخدمه الواجهة المحلية. بهذا لا نكتب أي شيء مرتين.

## 2. هيكل المستودع

```
aktool/
├── core/                      # النواة (Python 3.12)
│   ├── api/                   # FastAPI routers: firmware, sources, definitions, ai, review, json, sync
│   ├── vault/                 # تخزين BIN غير قابل للتعديل (sha256)
│   ├── identity/              # التعرّف: exact → variant → family → unknown
│   ├── importers/             # kp_json (من الكود الحالي), a2l, xdf, csv, manual
│   ├── validators/            # الفحوص الحتمية: النطاق، original_bytes، الأبعاد، المحاور
│   ├── knowledge/             # definitions, revisions, evidence, search (FTS5)
│   ├── review/                # Accept / Edit / Reject + audit
│   ├── jsonfactory/           # التصدير والاستيراد للأنواع الأربعة
│   ├── ai/                    # provider adapter, prompts, RAG, evals
│   ├── sync/                  # المزامنة بين المحلي والسيرفر
│   ├── db/                    # SQLAlchemy models + Alembic migrations
│   └── settings.py            # MODE=local|server
├── schemas/                   # الـ JSON Schemas الأربعة (مكتوبة كمسودة)
├── clients/
│   ├── streamlit_admin/       # الواجهة المحلية الحالية بعد تحويلها لعميل API
│   └── telegram_bot/          # البوت (aiogram)
├── deploy/                    # docker-compose, Caddy (HTTPS), backups
├── fixtures/                  # المجموعة الذهبية (خارج المستودع العام)
└── tests/
```

الكود الحالي في ECU Expert JSON Builder ينتقل كالتالي: `kp_parser.py` إلى `core/importers/kp_json.py`، وواجهة Streamlit إلى `clients/streamlit_admin`، وCLI يبقى أداة فوق الـ API.

## 3. الذكاء الاصطناعي

### طبقات القرار (من الأقوى للأضعف)
1. **فحوص حتمية**: hash، SW/CAL، original_bytes، حدود الملف. هذه لا تخطئ.
2. **استرجاع من المعرفة المعتمدة فقط** (RAG): البحث في السجلات approved وvalidated.
3. **اقتراح AI** بصيغة JSON مقيدة بالـ Schema، وكل ادعاء فيه يجب أن يشير إلى دليل.
4. **مراجعتك**: قبول، أو تعديل ثم قبول، أو رفض.

### ماذا يفعل الـ AI تحديداً
- تسمية الخرائط وشرحها، ومطابقتها مع أسماء A2L.
- اقتراح نفس الوظيفة في SW ID مشابه (والمحرك الحتمي يتحقق من البايتات).
- الإجابة عن أسئلتك من قاعدة المعرفة، عبر البوت أو الواجهة.
- **لا** يكتشف العناوين من تخمينه، و**لا** يكتب بايتات، و**لا** يعتمد شيئاً.

### Ollama
- **نموذج المحادثة والاقتراح**: نموذج تعليمات متوسط الحجم من عائلة Qwen أو Llama، بين 7 و14 مليار معامل. نبدأ بالأصغر ونقيس.
- **نموذج التضمين (embeddings)**: مثل `nomic-embed-text`، للبحث الدلالي لاحقاً.
- **المخرجات المقيدة**: Ollama يقبل JSON Schema في معامل `format`، فيُجبر النموذج على صيغتنا.
- **Provider Adapter**: طبقة واحدة تجعل تبديل Ollama بـ LM Studio أو مزود سحابي مجرد إعداد.

### كيف "يتعلم" النظام
- كل قبول أو تعديل أو رفض يُحفظ مع اقتراح الـ AI الأصلي، فيصبح لدينا أمثلة مُصحّحة.
- **مجموعة تقييم ثابتة** (المجموعة الذهبية): أي تغيير في النموذج أو الـ prompt لا يُعتمد إلا إذا تحسنت النتائج عليها، وأهم مقياس هو نسبة الإجابات الخاطئة الواثقة.
- **Fine-tuning بـ LoRA** يأتي لاحقاً فقط، عندما تتراكم مئات إلى آلاف الأمثلة المعتمدة.

## 4. السيرفر

### المرحلة الأولى (لك وحدك)
| البند | الاختيار | السبب |
|---|---|---|
| الخادم | VPS بـ GPU (ذاكرة 12 إلى 16 GB) أو VPS عادي + Ollama على جهازك | نموذج 7B يحتاج نحو 6 GB، ونموذج 14B نحو 10 إلى 12 GB بضغط 4-bit |
| التشغيل | Docker Compose: core + ollama + bot + caddy | تشغيل وتحديث بأمر واحد |
| HTTPS | Caddy (شهادة تلقائية) | بسيط وآمن |
| القاعدة | SQLite في البداية أيضاً | مستخدم واحد لا يحتاج Postgres، ونفس نماذج SQLAlchemy تنتقل لاحقاً |
| الحماية | مفتاح API + قائمة سماح لحسابك في Telegram | لا حسابات ولا تسجيل في هذه المرحلة |
| النسخ الاحتياطي | نسخة يومية للقاعدة والـ Vault مع manifest للـ hashes | حسب الوثيقة |

**خيار أرخص للبداية:** السيرفر بدون GPU، وOllama يعمل على جهازك ويتصل به السيرفر عبر نفق آمن. يصلح للتجربة، لكن البوت يتوقف إذا أُطفئ جهازك.

### لاحقاً (عند تعدد المستخدمين)
Postgres، وحسابات وعزل بيانات لكل مستخدم، وتشفير ملفات الـ Vault، وطابور مهام (مثل arq أو Celery) للتحليلات الطويلة.

## 5. المزامنة بين المحلي والأونلاين

- **المعرفة**: كل revision غير قابلة للتعديل ولها `record_id` ورقم، فالمزامنة إضافة فقط (append-only) ولا تحدث تعارضات كتابة فوق بعض. إذا عدّلت نفس السجل في المكانين تظهر revisionان متوازيتان وتختار أنت.
- **ملفات BIN**: تبقى محلية، ولا تُرفع للسيرفر إلا الملفات التي ترسلها بنفسك للبوت أو تختار مزامنتها.
- **الاتجاه**: الأوامر `sync push` و`sync pull` في البداية، ثم مزامنة تلقائية لاحقاً.

## 6. بوت Telegram

**المكتبة:** aiogram 3 (Python، نفس لغة النواة)، باستخدام webhook على نفس السيرفر.

**الحماية:** يتجاهل أي حساب غير حسابك (قائمة سماح بالـ user ID).

### الأوامر في النسخة الأولى
| الأمر | ماذا يفعل |
|---|---|
| إرسال ملف BIN | يحفظه في الـ Vault ويعيد تقرير الهوية: SW/CAL، والعائلة، وexact/variant/unknown مع الأدلة |
| إرسال ملف A2L/XDF/KP JSON | يستورده ويعيد تقرير الاستيراد |
| `/search` | بحث في المعرفة بـ SW ID أو اسم وظيفة أو كود DTC |
| `/ask` | سؤال للـ AI يجيب من المعرفة المعتمدة، مع ذكر المصادر |
| `/review` | يعرض الاقتراحات المعلقة بأزرار: قبول / رفض / فتح للتعديل |
| `/export` | يرسل لك ملف JSON لسجل معتمد |
| `/status` | حالة النواة وOllama وآخر نسخة احتياطية |

**حدود Telegram:** البوت يستطيع تنزيل ملفات حتى 20 MB عبر Bot API العادي، وهذا يكفي معظم ملفات ECU. للملفات الأكبر نشغّل Local Bot API Server على نفس الخادم.

**لاحقاً:** Mini App لعرض الخرائط والمقارنة والمراجعة المريحة، ثم التعديل على نسخة جديدة بالشروط التي اتفقنا عليها (تطابق تام، فحص البايتات، checksum للعائلة، تأكيدك).

## 7. ترتيب التنفيذ المقترح

| # | المرحلة | الناتج |
|---|---|---|
| 0 | العقود | الـ Schemas الأربعة + أمثلة + نقل kp_parser |
| 1 | النواة الأساسية | Vault + قاعدة البيانات + API للملفات + `MODE=local/server` |
| 2 | JSON Factory والفحوص | تصدير واستيراد بدون فقدان، ورفض البايتات غير المطابقة |
| 3 | **نشر مبكر على السيرفر + بوت بسيط** | رفع BIN عبر البوت والحصول على الهوية، وهذا أول استخدام أونلاين فعلي |
| 4 | المعرفة والمراجعة | البحث، و`/review` في البوت |
| 5 | المستوردات | A2L ثم XDF |
| 6 | الذكاء الاصطناعي | Ollama + RAG + `/ask` + مجموعة التقييم |
| 7 | الواجهة المحلية | Streamlit كعميل API، ثم دراسة romHEX14 |

وضعت النشر والبوت في المرحلة 3، مباشرة بعد أن تصبح للنواة وظيفة حقيقية، حتى تستخدمها أونلاين مبكراً كما طلبت، دون انتظار نهاية المشروع.

## 8. قرارات مطلوبة منك
1. **السيرفر**: VPS بـ GPU من البداية، أم VPS عادي وOllama على جهازك للتجربة؟
2. **المستودع**: إنشاء مستودع GitHub خاص للمشروع حتى أعمل عليه مباشرة.
